# Модель угроз

Глава говорит, от кого Aurix защищает, что он им гарантирует и чего явно не гарантирует. Она
дополняет [модель безопасности](../concepts/security.md), описывающую механизмы; здесь — о
допущениях, стоящих за ними. Отчёт, который ломает одну из строк раздела «Защищено», — это
уязвимость, см. `SECURITY.md` в корне репозитория.

## Активы

| Актив | Где живёт | Владелец |
|---|---|---|
| Голос (кадры Opus/PCMU, миксы), позиции, состояние речи | Память ноды, датаграммы AURX/QUIC/WebRTC, cascade-релеи, записи | Игрок |
| Текстовый чат, транскрипты, переводы | Нода, Postgres (опциональная история), провайдеры STT/MT | Игрок |
| Идентичность: user id, session id, членство в каналах, гранты | JWT игрока, память ноды, зеркало в Redis, Postgres | Игровой бэкенд |
| Секреты тенанта: API-ключи (хэш), секреты вебхуков, `media.cascade_secret`, ключ подписи JWT, общий секрет TURN | Postgres / конфиг / окружение | Оператор |
| Записи, evidence-клипы, экспорты | Диск ноды или S3-совместимое хранилище | Оператор (от имени игры) |
| Админ-аккаунты, аудит-лог, аналитика | Postgres | Оператор |
| E2EE identity- и sender-ключи | Только клиент | Игрок |

## Акторы и доверие

| Актор | Доверяем в | Не доверяем в |
|---|---|---|
| **Оператор** (держит ноды, PG, Redis, TURN) | Во всём, что видит нода: plaintext-медиа в не-E2EE каналах, записи, метаданные | Содержимое каналов `e2ee: true` (только шифртекст, но видно, кто, когда и сколько говорит) |
| **Игровой бэкенд** (держит API-ключ) | В своём тенанте: выпуск токенов игрокам, каналы, модерация, вебхуки, экспорты | Чужие тенанты (каждый ресурс ограничен тенантом, кросс-тенантные запросы отвечают `404`) |
| **Игрок** (держит JWT) | Говорить/слушать в каналах из токена, свои настройки, чат где разрешён | Чужие сессии, не выданные каналы, модерация без гранта, решения серверного микширования |
| **Анонимный узел сети** | Ни в чём | Во всём: не может открыть сессию, инжектировать медиа в чужую сессию, ретранслировать через TURN, заставить ноду делать неограниченную работу |
| **Другая нода флота** | Cascade-релеи, аутентифицированные `media.cascade_secret`; записи в реестре PG/Redis | Выдавать себя за клиента (у неё никогда нет сессионного ключа), читать E2EE-содержимое |
| **Сторонние провайдеры** (STT, TTS, MT, классификаторы модерации, получатели вебхуков, S3) | Только в данных, которые оператор настроил им отправлять | Обратные вызовы в ноду вне документированных эндпоинтов; нахождение в приватных сетях (SSRF-guard) |

## Защищено

| Угроза | Защита | Проверяется |
|---|---|---|
| Поддельные или воспроизведённые медиа AURX/QUIC (подмена SSRC, replay, порча бит) | AES-256-CTR + HMAC-SHA256 с ключами сессии, окно anti-replay на сессию, подписанный `SessionBind` до приёма любого медиа, QUIC-соединение привязано к сессии этим bind'ом | unit-тесты `protocol`/`quic`, `fuzz/aurx_packet`, живой E2E |
| Перехват сессии с другого адреса / злоупотребление миграцией соединения | Медиа принимается только с привязанного адреса/соединения; свежий подписанный bind побеждает, устаревшие соединения закрываются | тесты `quic`: stale connection, replay early data |
| Кросс-тенантный доступ через REST/WS API | Тенант — только из проверенного credential; каждый запрос ограничен `app_id` | isolation-тесты `e2e_live`, unit-тесты `api` |
| Кража и replay токенов | Короткоживущие JWT, одноразовые action-токены (`jti` захватывается атомарно), одноразовые ротируемые resume-токены, tombstone'ы после удаления | тесты `auth`, E2E `TOKEN_REUSED` |
| Злонамеренный или сломанный клиент валит ноду мусором на входе | Ограниченные, проверяющие границы парсеры AURX, RTP, STUN/TURN, control-JSON, E2EE-кадров, Opus, Ogg, WAV, live-кадров; корпус проигрывается на stable, libFuzzer с ASan — на nightly | `fuzz/` (12 целей), CI-job `fuzz` |
| Исчерпание ресурсов одним тенантом или IP | Лимиты на IP и на ключ (fleet-wide через Redis), лимит участников на ноду, лимит каналов на сессию, ограниченные очереди вебхуков/live-стримов/E2EE-ключей, максимальные размеры пакетов | rate-limit-тесты `control`, нагрузочные тесты |
| Открытый TURN-релей | MESSAGE-INTEGRITY с временными credentials, nonce, владение аллокацией, permissions | тесты `turn`, `fuzz/stun_message` |
| Инфраструктура оператора используется против его же сети (SSRF) | Исходящие URL валидируются, приватные/link-local отклоняются, DNS пинится на доставку, редиректы не следуются | тесты `net` |
| Получатели вебхуков принимают поддельные события | Подпись HMAC-SHA256 с timestamp, сравнение за константное время, общий тест-вектор во всех SDK | тесты `webhooks`, `fuzz/webhook_signature`, тесты серверных SDK |
| Понижение E2EE-канала до plaintext | Нода дропает plaintext в каналах `e2ee: true` и отказывает неспособным сессиям | тесты `router`, живой E2E |
| Другая нода флота инжектирует медиа | Relay-конверты аутентифицированы cascade-секретом, неизвестные адреса источников дропаются, лимит хопов | тесты `cascade`, живой E2E на 4 нодах |
| Повышение привилегий между админ-ролями | Матрица прав проверяется на каждом админ-роуте; SSO-claims маппятся в роли на сервере | E2E `admin` с mock IdP |
| Supply-chain: уязвимые или нелицензионные зависимости, подменённые артефакты релиза | `cargo audit` + `cargo deny` в CI, сборки с `--locked`, bundled libopus запинен версией crate, SBOM + SHA-256 (+ подписи Sigstore, когда подпись релизов настроена) | CI `audit`, release-workflow |

## Не защищено (по замыслу)

* **Злонамеренный оператор в не-E2EE каналах.** Нода микширует, записывает и транскрибирует
  plaintext — это и есть продукт. Где оператор не должен слышать — включайте `e2ee: true`.
* **Злонамеренный оператор против привязки E2EE-идентичности.** Ноды ручаются за публичные
  identity-ключи; оператор мог бы подставить свои. Приложениям, которым нужна эта гарантия,
  следует сравнивать отпечатки вне канала. Анализ трафика (кто, когда и сколько говорит) виден
  всегда.
* **Скомпрометированный игровой бэкенд.** Кто держит API-ключ, тот и тенант: он может выпускать
  токены любому пользователю тенанта и читать его записи. Держите ключ на сервере
  ([token-серверы](../backend/server-sdks.md)), ротируйте, ограничивайте ключи нужными правами.
* **Атаки на стороне клиента.** Читер может замьютить себя, слать тишину, слать мусорное аудио
  внутри валидной сессии или запустить модифицированный SDK. Aurix аутентифицирует, *кто*
  отправляет, а не честность аудио; голосовая модерация — это слой политики
  ([content safety](../features/safety.md)).
* **Отказ в обслуживании сверх ёмкости ноды.** Лимиты и капы защищают одну ноду от одного
  нарушителя; объёмные UDP-флуды — задача сетевого уровня (ставьте ноды за DDoS-защиту
  провайдера, ограничивайте диапазоны `media.bind`).
* **Побочные каналы в libopus, AES или ОС.** Используются константно-временные примитивы
  RustCrypto и upstream libopus; устойчивость к физическим и микроархитектурным атакам на общих
  хостах не заявляется.
* **Корректность сторонних провайдеров.** Вывод STT/MT/классификаторов — то, что вернул
  провайдер; вердикты модерации — сигналы, а не доказательства.

## Инвентарь поверхности атаки

Байтовые парсеры, достижимые до аутентификации, у каждого — fuzz-цель в `fuzz/`:

| Поверхность | Точка входа | Цель |
|---|---|---|
| Датаграмма AURX (UDP, QUIC datagram, WS-туннель) | `AurixPacket::decode`/`decode_bounded`, `open`, `relay_inner*`, `parse_session_bind` | `aurx_packet` |
| WebRTC RTP | `RtpHeader::parse` | `rtp_header` |
| STUN/TURN | `StunMessage::decode`, `verify_integrity`, `verify_fingerprint`, XOR-адреса | `stun_message` |
| Control WebSocket (JSON) | round-trip десериализации `ControlMessage` | `control_message` |
| Релей E2EE-ключей и кадры | `SenderKey::open`, `PeerKeys::open`, `IdentityKey::unwrap`, стейт-машина `Group` | `e2ee_frame` |
| Opus-полезная нагрузка (C-библиотека) | `aurix_opus::Decoder`, парсер DRED, инспекция пакетов | `opus_packet` |
| Даунлинк клиента | `RemoteMixer::push_wire_frame` + `mix` с враждебными кадрами | `remote_mixer` |
| Загрузка записей / вход mixdown | `parse_ogg_opus` | `ogg_opus` |
| Ответы TTS-провайдера | `parse_wav` | `wav` |
| Pull-коннекторы live-стримов | `live::decode_frame` | `live_frame` |
| Заголовок подписи вебхука | `verify_signature` | `webhook_signature` |
| Короткие строки (TURN-имена, курсоры, роли, адреса, URL) | разные `parse`-хелперы | `text_parsers` |

Аутентифицированные поверхности (тела REST, WS-команды после `SessionInit`) покрыты
интеграционными и E2E-наборами, а не фаззингом; serde отклоняет неизвестные формы до хендлеров.

## Запуск фаззеров

```bash
# Stable: проиграть закоммиченный корпус + edge-входы (то же делает CI на каждый push).
cargo test --manifest-path fuzz/Cargo.toml --release

# Nightly + libFuzzer/ASan (Linux/macOS):
cargo install cargo-fuzz
cargo +nightly fuzz list
cargo +nightly fuzz run aurx_packet fuzz/corpus/aurx_packet -- -max_total_time=600 -max_len=4096

# Перегенерировать детерминированные seed'ы после изменения wire-формата:
cargo test --manifest-path fuzz/Cargo.toml --release -- --ignored seed_corpus
```

Падения ложатся в `fuzz/artifacts/<target>/`. Минимизируйте `cargo fuzz tmin`, добавьте
уменьшенный вход в `fuzz/corpus/<target>/` под говорящим именем (`regress_<что>`) вместе с фиксом —
тогда stable-replay сторожит регрессию. В git попадают только именованные seed'ы и `regress_*`;
входы с SHA-1-именами, которые libFuzzer накапливает в том же каталоге, игнорируются.
